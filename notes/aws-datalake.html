AWS DataLake

2025.07.02

  • datalake를 통해 data ingest가 빨라진다. schema only를 사용해서
    • EAT 패턴 : 추출을 해서 로드를 하고 트랜스폼해서 바로 사용하기 때문에 빠른 ingest라고 표현한다 ( transform 단계를 많이 최소화, 정규화 같은 것들)
  • Storage, Computing이 decoupled 되어있기 때문에 데이터를 독립적으로 조정할 수 있다.
  • Apache, 하둡 사용하는 듯
  • 기존의 DB에서, 데이터 무결성이나 쿼리 처리 등을 위해서 굉장히 복잡하고 헤비한 베이스들이 있었는데, 이걸 DataLake로 해결을 한다.
    • 처음에는 storage를 위한 용이었음.
    • “단일 플랫폼” ← 오픈 테이블
    • ACID transcaction, query support
  • Iceberg
    • Spark, Hive를 같은 OTF에서 처리할 수 있다.
    • Iceberge 쿼리 엔진을 통해 SQL 처리 가능
  • Catalog → Metadata → Data layer로 구성된다.
    • Catalog: 최신의 메타데이터를 포인팅하고 있음.
  • 히든 파티션, 파티션 transform
    • Split plan으로 data할 때 쿼리 재작성 없이 WHERE 등의 SQL 쿼리 처리 가능하다.
  • Tagging, branching
    • tagging을 해서 expire를 막는거고
  • S3
    • tableau form의(parqeut 가장 많음) 데이터 S3 저장이 늘어남에 따라
    • scale up이 필요했고, 유지 관리에 대한 코스트가 높앗다.
  • S3 Table
    • Iceberg 형태의 OTF를 네이티브하게 저장한다.
      • 따라서 ARN을 가진다 → 활용성이 높다
  • 기존 DBMS와의 가장 큰 차이점은 무엇인가?
    • Storage/Computing layer가 DBMS에서는 동일한 반면에 Storage기능에서 Athena와 같은 컴퓨팅 엔진으로 쿼리접근하는게 가장 큰 차이다.
