GNN message passing

2026.07.20

GNN과 message passing vs Node2Vec

현재 우리 모델은 STRING graph를 Node2Vec로 압축한 frozen 임베딩으로만 활용. GEARS류 모델은 graph 위에서 GNN message passing으로 라이브 query. 이 차이가 combo 일반화 성능 gap의 본질.

1. Node2Vec vs GNN — 한 줄 요약

  • Node2Vec: graph 데이터를 학습 전에 한 번 압축해 만든 고정 사전 (gene → 128-dim 벡터).
  • GNN: graph 자체를 모델의 한 layer로 두고, 매 forward pass마다 라이브로 query하는 inference 엔진.
Node2VecGNN
그래프 사용 시점학습 전 1회 (random walk)training/inference 매번
출력노드당 고정 벡터forward마다 새 임베딩

비유사람별 "성격 카드" 정적"A가 화났다" 소문이 친구→친구로 퍼짐

결정적 차이: Node2Vec은 같은 gene을 어느 상황(A가 KO됐든 안 됐든)에서나 항상 같은 벡터로 표현. GNN은 perturbation 상태에 따라 상황별로 다른 임베딩.

2. Message passing — 동작 원리

Message passing = 그래프에서 각 노드가 자기 이웃들과 정보를 주고받아 자기 표현을 업데이트하는 과정.

구체 예시 (gene 4개)

graph:
   A ─── B
   │     │
   C     D
  • A의 이웃 = {B, C}
  • B의 이웃 = {A, D}
  • C의 이웃 = {A}
  • D의 이웃 = {B}

초기 상태 (layer 0)

각 노드에 feature vector 부여. perturbation task라면 "이 gene이 KO됐는가?" bit도 포함. A가 KO된 상황을 가정:

\[ \begin{aligned} h_A^{(0)} &= [\,\text{is\_perturbed}=1,\ \ \text{gene\_A\_features},\ \ldots\,] \\ h_B^{(0)} &= [\,\text{is\_perturbed}=0,\ \ \ldots\,] \\ h_C^{(0)} &= [\,\text{is\_perturbed}=0,\ \ \ldots\,] \\ h_D^{(0)} &= [\,\text{is\_perturbed}=0,\ \ \ldots\,] \end{aligned} \]

Layer 1 — A 노드 업데이트 3단계

1. SEND — 각 이웃이 A에게 메시지 보냄 (\(M\) = 작은 MLP/linear):

\[ m_{B \to A} \;=\; M\bigl(h_B^{(0)}\bigr), \qquad m_{C \to A} \;=\; M\bigl(h_C^{(0)}\bigr) \]

2. AGGREGATE — 받은 메시지들 합치기 (sum / mean / attention):

\[ a_A \;=\; \operatorname{sum}\!\bigl(\{\,m_{B \to A},\ m_{C \to A}\,\}\bigr) \]

3. UPDATE — A의 표현 갱신 (\(U\) = 또 다른 MLP):

\[ h_A^{(1)} \;=\; U\bigl(h_A^{(0)},\ a_A\bigr) \]

모든 노드가 동시에 같은 과정 수행. 결과:

  • \(h_A^{(1)}\) = A 자신 + B, C (1-hop) 정보
  • \(h_B^{(1)}\) = B 자신 + A, D (1-hop) 정보 ← B는 이제 "내 이웃 A가 KO됐다"를 안다

Layer 2 — 정보가 2-hop으로 확장

A가 받는 메시지는 이번엔 \(h_B^{(1)}\), \(h_C^{(1)}\) (이미 1-hop 정보 포함).

\[ h_A^{(2)} \;=\; U\bigl(h_A^{(1)},\ \operatorname{sum}\!\bigl\{\,M(h_B^{(1)}),\ M(h_C^{(1)})\,\bigr\}\bigr) \]

→ \(h_A^{(2)}\) = A 자신 + 1-hop + 2-hop (B 거쳐 D까지)

핵심: layer 수만큼 멀리 정보가 전파됨. 보통 2~4 layers면 충분 (over-smoothing 방지).

3. perturbation context에서 message passing의 위력

\(h_A^{(0)}\)의 첫 차원에 "A is KO" 비트를 넣으면:

  • Layer 1 후 → B, C가 "A가 KO됐음"을 자기 임베딩에 반영
  • Layer 2 후 → D도 (B를 거쳐) 안다
  • graph 위의 perturbation 신호가 흐름이 임베딩에 자동 코딩

Combo (A, B) 동시 perturbation에서 더 강력

  • 초기 feature에 A와 B 둘 다 is_perturbed=1 표시
  • message passing → 두 신호가 graph 위에서 동시에 퍼지며 공통 이웃에서 합쳐짐
  • 그 노드의 최종 임베딩이 "A와 B 둘 다 perturbed인 상황 하 자기 상태"를 코딩
  • 모델은 이 임베딩을 보고 combo 효과 예측

→ graph 구조 자체가 combo 일반화의 매개체. 안 본 combo (X, Y)도 X, Y의 graph 이웃들이 학습된 다른 combo와 겹치면 자연스럽게 일반화됨.

4. 우리 모델 현재 구조 vs GEARS 비교

우리 모델 현재 (Node2Vec)

STRING graph
    │ (offline, build_string_node2vec.py)
    ▼
random walk → skip-gram → gene_table.npy (16202 × 128)  [frozen]
    │
    ▼ (training/inference 시 lookup만)
KGObjectEncoder: slot_id → name_to_row → frozen vector
    │
    ▼
proj + gate + residual + perturb_bits → slot embedding (67-dim)
    │
    ▼
2 slots [gene_a, gene_b] sum → conditioning context
    │
    ▼
drift network → SDE simulation

문제: graph 정보는 frozen 벡터에 압축되어 모델이 못 query. combo \((A, B)\)에 대해 모델은 그저 \([\,\text{N2V}(A),\ \text{N2V}(B)\,]\) 두 벡터만 받음. "A와 B가 graph에서 이웃이다"라는 정보 자체가 없음.

GEARS (GNN message passing)

GO graph (BP terms + gene → term annotations)
    │
    ▼ (model의 일부, 매 forward pass)
GNN layers (message passing, perturbation-conditional)
    │ (perturbation 비트가 feature로 들어가서 신호가 graph 위에서 전파)
    ▼
context-aware gene embedding (combo 상황에 맞게 매번 새로 계산)
    │
    ▼
fold change predictor

강점: 안 본 combo도 graph topology로 일반화. 학습 때 본 다른 combo의 패턴을 graph 이웃 관계를 통해 transfer.

6. 향후 개선 방향

  1. GNN encoder 도입 (1순위) — STRING/PCNet graph 위에서 message passing. perturbation feature를 노드에 얹어 전파.
  2. 명시적 interaction module — combo (A, B)에 attention/bilinear pooling 추가.
  3. multiplex graph — STRING (PPI) + PCNet (functional consensus) + GO (semantic hierarchy)를 별도 채널로 결합.

KG source 단순 교체 (STRING → PCNet)는 임베딩 quality 5~10% 개선 정도만 기대. architecture 변경 (GNN message passing)이 진짜 차이를 만든다.

8. static vs GNN — 두 축: ① 관계형(GNN) × ② 응답-구조 그래프

§7 발견을 한 장으로: prior가 안 본 perturbation을 돕는가 = ① 관계형(이웃에서 조립) 이면서 ② 그래프가 응답 유사도를 담느냐. 둘 다 필요.

두 방식 (object 토큰 생성)

static (frozen lookup)GNN (message-passing)
토큰e_A = proj(고정 벡터_A)e_A = proj(GNN(A; 이웃의 학습 상태, edges))
그래프 사용학습 전 1회 (오프라인 압축)매 forward 라이브 query
같은 object항상 같은 벡터이웃 상태 따라 갱신
geneSTRING node2vec lookupSTRING/GO/coexpr 위 전파
drugLINCS 시그니처 lookup (=배포 prior)Tanimoto/LINCS 위 전파

안 본(unseen) object에서 — 핵심

  • static: 고정 벡터가 응답 기하와 어긋나면 틀린 좌표를 박고 모델이 못 고침(frozen) → no-KG보다 해로움.
  • GNN: 안 본 object 토큰을 이웃(seen)의 학습된 상태에서 조립 → 이웃의 응답을 물려받음 = 전이. no-KG는 안 본 것에 좌표조차 없음.
  • → static = "고정 사전 찾기", GNN = "이웃에게 물어 그 자리에서 만들기". 안 본 것엔 물어볼 이웃(=응답 이웃)이 있느냐가 전부.

단, GNN이면 무조건 아님 — 그래프가 응답을 담아야 (§7)

static (아무 그래프나 고정)      → 해로움 (틀린 좌표 고정)
GNN + 구조 그래프(STRING/Tani)   → null/해로움 (이웃 ≠ 응답이웃)
GNN + 응답 그래프(coexpr/LINCS)  → 전이 성공 ✓

두 조건 다 필요: ① 관계형(GNN) 그리고 ② 응답-구조 그래프.

9. Gene coexpr-GNN 구조 — message-passing으로 안 본 유전자에 전이

개념도: control-coexpression 그래프(함께 변함=응답 이웃) 위에서 message passing → 안 본 유전자 X의 토큰이 seen 이웃(A,B)의 학습된 상태에서 조립됨 → drift → SDE. static lookup은 X에 좌표조차 없지만, GNN은 이웃에서 만들어낸다.
flowchart LR
  subgraph G["control-coexpression graph<br/>(edge = genes co-vary ⇒ response-neighbors)"]
    direction TB
    A["seen gene A · trained state"]
    B["seen gene B · trained state"]
    X["unseen gene X · no training"]
    A -->|coexpr edge| X
    B -->|coexpr edge| X
  end
  X -->|"GNN message passing:<br/>e_X = aggregate(neighbor states)"| E["object token e_X<br/>inherits A,B response"]
  E --> P["pooler → conditioning c"]
  P --> D["AdaLN-Zero force field → drift u_θ"]
  D --> S["Euler-Maruyama SDE →<br/>predicted response of unseen X"]
  • 핵심: 바뀜은 토큰 생성(그래프 위 전파)뿐, pooler·AdaLN·SDE는 불변.
  • 왜 coexpression 그래프여야 (§7/§8): 이웃이 응답 이웃이어야 전파가 응답으로 이어짐 — STRING(상호작용)·GO(주석)은 이웃≠응답이웃이라 전이 실패.
  • static vs 이 구조 비교 + 실측은 §8 및 [[#10 관계형 그래프 인코더 (STRING/GO/coexpr) — 응답-구조 그래프만 both-unseen 전이]].

10. Node2Vec vs GNN 대비 (개념도)

§1 표·§4 ASCII를 한 장으로: Node2Vec = 학습 전 그래프를 고정 벡터로 압축 → lookup(상황 무관, 안 본 객체엔 좌표 없음). GNN = 그래프를 모델 layer로 두고 매 forward 이웃에서 라이브 조립(상황별 갱신, 안 본 객체는 이웃에서 전이).
